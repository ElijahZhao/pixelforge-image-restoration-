# 算力台账：34 次内核、29.1 小时机上时间

> 这份台账记录 2026-11-01 → 11-03 在 Kaggle 免费 T4 上跑过的**每一次**内核。
>
> 时长不是估的：每一行都由 `kaggle kernels logs` 返回的日志逐条时间戳算出（取最后一条事件的相对秒数），
> 起点用 `kaggle kernels files` 的产物创建时刻。复算脚本是 `scripts/kernel_ledger.py`，
> 逐行数据在 `results/compute_ledger.csv`，原始证据在 `results/kernel_runs.json`。

## 一、四个数字

| 指标 | 数值 | 说明 |
|---|---|---|
| 内核 run 次数 | **34 次完成** | 覆盖 13 个内核、34 个版本 |
| 墙上时间合计 | **29.05 h** | GPU 21.72 h + CPU 7.33 h |
| 其中完全失败 | **6.84 h**（11 次，占 24%） | 另有 4 次部分成功，见第四节 |
| 训练净时长 | **13.5 h** | 1 700 个 epoch，扣掉环境与数据下载后的纯训练时间 |

Kaggle 的周配额只扣 GPU 会话。**对账内核（`protocol-repo`）刻意关掉了 GPU**（`enable_gpu: false`），
因为它要证明"任何人 clone 下来都能复现"，不能依赖显卡——这 7.33 h 一分 GPU 配额都没花。

## 三、两条线并行

GPU 和 CPU 不是串行排队等着的。**A 批训练（23:10 起）与对账 v1（23:56 起）在同一天晚上并行**，
**B 批训练（09:44 起）与对账 v3（09:48 起）在同一个上午并行**——两次重叠合计 6.6 h。
把重叠算进去，29.05 h 的机器时间压在 **52.3 h 的日历跨度**上
（11-01 20:11 → 11-04 00:27 CST），**机器有 56% 的时间在算**。
夜里空档主要是等训练跑完没起新内核，不是配额排队。

第三条并行是最后加的：**C 批与 D 批拆成两个内核同时跑**（`seed-matrix` v6 与 `seed-matrix-d` v1，
17:40 前后同时起跑）。原本 D 批要等 C 批跑完再推版，因为 Kaggle 只保留每个内核的**最新版本产物**，
推新版会覆盖旧版。现在两批各占一个内核，产物目录互不干扰，这个约束从根上消失，
墙钟省下约 2 h。代价是 GPU 周配额同时被两条线占着。

第四段跨度是 11-03 15:36 → 19:19，中间 5.3 h 里 C 批跑了 3.70 h、D 批跑了 1.61 h，
加上 A/B 两批与三次 CPU 对账的间隙——**这 5.3 h 里机器几乎没停**。

代价是有的：并行时段里 GPU 内核的启动要排队，A 批 v4 的日志显示环境探测用了 16 s、
3.5 GB 的 DIV2K 训练集下载用了 144 s（每次训练都要重下，Kaggle 不缓存）。

## 四、11 次完全失败，6.84 小时

失败不是意外，是这类工作的主要成本。逐条列在这里，包括被我们自己判定作废的。
另有 4 次**部分成功**（拿到一部分数、剩下的作废），不计入这 6.84 h。

| 内核 · 版本 | 烧掉 | 失败原因 | 怎么修的 |
|---|---|---|---|
| `eval-protocol` v2 | 7.2 min | LOL 验证集路径 `/kaggle/working/repo/data/lol/val/low` 不存在 | 改从 HuggingFace parquet 读 |
| `eval-protocol` v3 | 1.1 min | 仓库里的 `train/datasets.py` 遮蔽了 HF 的 `datasets` 包，`load_dataset` 导入失败 | 改名模块、换 import 方式 |
| `perceptual-ablation` v1 | 3.0 min | `os.symlink` 目标已存在，`FileExistsError` | 软链改成幂等（存在就跳过） |
| `protocol-matrix` v2 | 54 s | 第二版权重在工作目录找不到 | 加查找路径 |
| `protocol-matrix` v3 | 48 s | 改用 base64 内嵌，但模块没生成 | 内嵌脚本单独跑 |
| `protocol-matrix` v4 | 48 s | 内嵌权重体积对不上 | 核对 md5 |
| `protocol-repo` v1 | **3.23 h** | 锚点配错：拿 27.47 去比 P3（tv_aa），x2 差 0.112 dB 超容差 0.10 → 判 FAIL | 拆出只换算子的 P7 / P8，锚点重定；容差没放宽 |
| `protocol-repo` v2 | 12 s | commit pin 写了短哈希，`HEAD != pinned` 断言拦截 | 改完整 40 位哈希 |
| `protocol-repo` v3 | **3.37 h** | x2 单协议 CPU 评估超 7200 s 被 kill | 拆成单协议、timeout 收到 6600 s |
| `protocol-full` v1 | 1.2 min | 锚点 gate 拦下：`pil_bicubic` 经 PIL 返回 CPU tensor，模型在 CUDA | `build_lr` 结果加 `.to(DEVICE)`；**这道门禁 1 分钟买下后面 80 分钟** |
| `protocol-full` v2 | 35.3 min | 低光 U-Net 尺寸错位（76 vs 75）+ 基线 `stdev(inf)` | 加 `--align`（pad→前向→裁回）；inf 排除并记 `n_inf`。SR 10 ckpt 仍有效 |
| `protocol-full` v3 | 8.1 min | 低光把 `high` 降质当输入，且多传 `--scale 2` | 改配对输入（读 `low/`），`scale` 锁 1 |

其中 `protocol-repo` v1 与 v3 两次就烧掉 **6.6 h**，占全部失败时间的 96%。
新增的三次 `protocol-full` 失败合计只有 **0.74 h**——因为每次都是**先跑门禁再烧算力**：
v1 的锚点 gate 1 分钟退出，v2/v3 都是低光单任务，作废的只是那一段。
它们是 CPU 内核，不花 GPU 配额——这是当时把对账放到 CPU 上的直接收益。

## 六、配额

- Kaggle 免费额度：T4，30 h / 周（周六 00:00 UTC 重置），￥0。
- 本周已用（GPU 部分）：**21.72 h**（34 次 run 的台账读数，含探针 0.02 + 矩阵四版 0.86）。
- 剩余可用：**约 8.3 h**（30 h 减去已用；周配额每周六 00:00 UTC 重置）。
- **阶段 5 已全部跑完，不再需要 GPU**：3 任务 × 5 种子 × 8 协议（低光 5 协议）
  加两条参照线，Kaggle 侧四版合计 **0.86 h**（v1 1.2 min + v2 35.3 min + v3 8.1 min + v4 7.1 min = 0.861 h，含一次作废的 v1）；
  ×2 基线另在本地 CPU 跑，13.5 min、0 配额。
- **比早期的 4.2 h 拍脑袋估算低约 5 倍**（4.2 / 0.86 = 4.9×）。
  ⚠️ 早先这里写"低一个量级"并用"T4 加速比 66×"解释——**两处都不成立**：
  4.2 → 0.86 只有 4.9 倍，不到一个量级；而 **66× 这个数全仓没有推导，也没有单图 CPU 前向的实测做分母**
  （台账里只有"整套矩阵"的 CPU 耗时：`protocol-repo` v3 3.37 h / v4 43.8 min，不是同口径）。
  4.2 / 0.7（探针外推的预测值）= 6×，也对不上 66×。**66× 已列为禁写**，见 `paper/FACTS.md` §10-E17。

C 批与 D 批**并发**跑，因此墙钟只等 1.8 h 而不是串行的 4 h；配额按各自运行时长累计，并发不额外扣。

## 七、怎么复算

```bash
python scripts/kernel_ledger.py --out-dir results
```

脚本会遍历 13 个内核的各个版本，拉执行日志与产物清单，重新生成
`results/compute_ledger.csv` 与 `results/kernel_runs.json`。
日志会缓存在 `.cache/kaggle-logs/`——Kaggle 对"正在运行的内核"的历史日志查询不稳定，
缓存让重跑不依赖 API 的临时状态。

正在运行的内核不会进入 CSV：日志接口对运行中的内核返回空数组，脚本因此跳过它们。
两个批次跑完后重跑本脚本，它们的 run 就补进去了。

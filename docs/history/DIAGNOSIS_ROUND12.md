## 二、配对逻辑：这次是对的（推翻自己的两个假设）

我本来准备在第 12 轮下两个结论，结果都被实验推翻：

### 假设 A："随机 crop 让 low/high 错位"

`LowLightDataset.__getitem__` 对 low 和 high **用同一个随机 `(i,j)` 裁剪、同一个概率翻转**：

```python
i = torch.randint(...)
j = torch.randint(...)
low  = TF.crop(low, j, i, crop_size, crop_size)
high = TF.crop(high, j, i, crop_size, crop_size)   # 同一 (i,j)
if augment:
    if torch.rand(1) < 0.5:
        low, high = TF.hflip(low), TF.hflip(high)  # 同一概率
```

实测（合成 LOL，low = high × 0.16）：

```
low/high 平均比: 0.149  (构造值为 0.16)
=> OK 空间对齐
```

**结论：配对逻辑本身正确。** 我之前的担心是多余的——只要文件名和尺寸一致，这里不会错位。
（所以"随机裁剪导致错位"不成立，但我第 11 轮已经把"随机裁剪导致指标不可信"降级过一次，
这次是**第二处被我自查推翻**的直觉。）

### 假设 B："SR 的 `crop_size // scale` 产生奇数尺寸"

```
scale=2: HR 96 -> LR 48 -> PixelShuffle放大 96   OK
scale=4: HR 96 -> LR 24 -> PixelShuffle放大 96   OK
```

整除没问题。实测 SR 的 `lr` 确实是 `hr` 的 bicubic 下采样：

```
datasets 的 lr 与 '同crop同插值再下采样' 差: 0.0000 / 255
=> lr 是 hr 的确定下采样（非独立随机图）
```

**结论：SR 配对逻辑正确。**

> 诚实修正：第 12 轮初我对数据层最悲观的两个猜测，都被实验否掉了。
> 这说明我前面的"直觉式怀疑"需要被实验压住——好在这一轮压住了，否则又会多一个夸大的结论。

## 三、但鲁棒性几乎是零（真实的、可复现的缺陷）

配对逻辑对"干净数据"正确，但**对真实数据集常见的脏输入完全没有防护**。实测：

| 输入情形 | 行为 | 后果 |
|---------|------|------|
| low/high **数量不一致** | `IndexError: list index out of range` | 直接崩，训练中止 |
| **损坏文件**（不是合法图片） | `UnidentifiedImageError` | 直接崩，无跳过 |
| low/high **尺寸不同**（如 100×120 vs 110×130） | **不崩** | **隐性错位**——同一 `(i,j)` 裁到不同空间区域 |
| 灰度/彩色混用 | 侥幸不崩（靠 `convert("RGB")` 兜底） | 侥幸正确，但无显式校验 |

**其中第 3 行是最危险的，因为它是"沉默的"——不报错、不告警、训练照跑。**

```
low(100x120)/high(110x130) 不同尺寸 → 未崩溃
  low=(3,128,128)  high=(3,128,128)
  警告：low 与 high 用同一 (i,j) 裁剪，但尺寸不同→裁到【不同空间区域】，配对隐性错位
```

模型此时学到的，是"把图 A 的某个区域，映射到图 B 的另一个区域"——监督信号在本质上
是**错误配对**，却不会触发任何报错。这比"直接崩"更糟，因为它会安静地污染训练。

> 这正好印证了第 11 轮的结论："尺寸约束在三个模块被各自定义（训练 resize / 推理 pad /
> 模型要求整除），没有单一事实来源。" `datasets.py` 假设 low 和 high **严格同尺寸**，
> 但代码里没有任何断言或校验来保证这一点——它只是"碰巧对干净数据成立"。

## 四、更深一层：数据管线对"训练/推理尺寸不一致"的纵容

第 8、11 轮都点出过低光的"尺寸三处各表"。本轮把数据侧补完：

- **训练时**（`LowLightDataset`）：若图小于 `crop_size=128`，`TF.resize` 到 128×128
  ——**改变几何，破坏原始分辨率信息**。
- **推理时**（`model_loader._pad_to_multiple`）：pad 到 32 倍数（**不改几何**，但补零边界）。
- **模型**（`LowLightUNet`）：要求边长整除 32，否则解码器 concat 崩溃。

三处规则各写各的，且**没有任何一处校验"训练输入尺寸 == 推理输入尺寸"**。
于是：模型在 128×128 上训练，在全图上推理，中间还有 pad/rescale 的语义差异。
第 10 轮的"亮度 137.7 过曝"、第 8 轮的"17.6/255 数值差"，一部分根子就在这里。

---

## 五、一个该被表扬的点（必须说清楚）

`datasets.py` 对"图尺寸 < crop_size"做了兜底（resize 而不是崩），对灰度做了 `convert("RGB")`
兜底。这种**对干净数据的容错**是合格的。问题在于：**它只防了"小图/灰度"这两类，
没防"数量不一致/损坏/尺寸不同"这几类**，且最危险的那类（尺寸不同）恰好是"不报错"的。

---

## 六、本轮结论

把第 12 轮钉在几个点上：

1. **数据管线的"配对逻辑"是正确的**——lr/hr、low/high 的对应关系在干净数据上成立。
   我原本准备下的两个悲观结论（随机 crop 错位、整除问题）都被实验推翻。
2. **数据管线的"鲁棒性"几乎为零**——数量不一致崩、损坏文件崩、尺寸不同则**沉默地错位**。
   最后一种最危险：不报错、不告警、训练照跑，但监督信号在本质上已被错误配对污染。
3. **尺寸约束三处各表、无单一事实来源**这一结论，本轮从数据侧得到补齐——
   它是第 8/11 轮"训练/推理尺寸不一致"问题的上游根因之一。

**统一到一句话：**

> **数据管线在"理想数据"上是诚实的，在"真实数据"上是脆弱的。**
> 而真实数据集（DIV2K / LOL）几乎必然会包含"尺寸不完全对齐、偶有损坏、命名偶有不规"的样本——
> 这些恰好落在数据层没有任何防护的盲区里。**最糟的是那个"沉默的错位"：它不会报错，只会产生一个
> 表面上能训练、实则学到错误监督信号的模型。** 这和第 9 轮"测试只测形状不测契约"、第 11 轮
> "缺陷彼此掩盖"是同一个病灶的不同切面：**错误不发生在显眼的地方，发生在假设里。**

## 一、超参核查：写在文档里的配置

`PROGRESS.md` §2.5 记录的训练配置：

| 任务 | 配置 |
|------|------|
| SR ×4 | `--model generator --scale 4 --epochs 200 --batch_size 8 --lr 1e-4 --perceptual` |
| Lowlight | `--task lowlight --epochs 200 --batch_size 8 --lr 2e-4` |

**先看规模**（实测，不是文档自述）：

```
SRGenerator x4  参数: 1.224 M
LowLightUNet    参数: 0.565 M
SR 残差块数: 8
```

注意：文档里写的是"`sr_generator_scale4.pt`（**4.8M**）"、"`lowlight.pt`（**2.3M**）"。
这些数字是**文件字节大小**（5,031,991 / 2,308,978 bytes），**不是参数量**（1.224M / 0.565M）。
两个数字混在一起陈列，会让人误以为这是两个"大模型"。实际上都很小——尤其 SR 只有 1.2M 参数、
8 个残差块（真正的 SRResNet 论文用的是 **16 个**）。这是第 8 轮"容量退化变异被测试放行"的现实基础。

**超参本身的评价**：`lr=1e-4`、`batch=8`、`epochs=200`、Adam + 余弦退火，对这类小模型是**合理配置**，
没有明显错误。也就是说，**模型学不好，不是超参的锅**——这排除了一个可能性，把问题更精确地指向损失函数。

## 二、损失函数的量级分析（本轮核心实验）

第 1 轮我下过一个结论：

> `loss = 0.01 * loss + percep(out, hr)` → 感知项占 99.2%，像素损失被抹除。

**本轮用真实数值重测，结果需要修正，而且修正后问题更深。**

用项目实际使用的 **pretrained VGG16** 做实验，量化两项的绝对量级与特征质量：

```
未归一化输入([0,1]直接喂) -> VGG特征均值=0.0503  零占比=94.2%
已归一化输入(ImageNet)    -> VGG特征均值=0.2441  零占比=88.6%
特征均值比(标准化/原始)   = 4.8 倍
```

两项损失的量级：

```
像素项 charbonnier      = 0.3315
感知项 percep           = 0.0035
0.01 * 像素项           = 0.003315
感知项 / (0.01*像素项)  = 1.1 倍
=> 感知项占比: 51.36%   像素项占比: 48.64%
```

**这个结果修正了第 1 轮"感知项占 99.2%"的说法。** 真实比例是**约 50/50**，不是 99/1。我第 1 轮的估算高估了。

**但修正后的图景其实更糟，原因在于：两个项各自都是坏的，却恰好抵消成"看起来差不多"。**

1. **像素项被乘小了 100 倍**（`0.01 * loss`）：Charbonnier/L1 原本是 0.33 量级，被压到 0.0033。
   模型对这个任务的主监督信号，被人为削弱了两个数量级。
2. **感知项因为未归一化而失真**：`[0,1]` 输入让 VGG 的 **94.2% 特征为零**（第 3 轮结论，本轮复现）。
   本该是"高层语义监督"的感知项，实际看到的是被压扁到近乎全零的特征图，其特征均值只有正确归一化时的 **1/4.8**。

> **关键洞察**：`0.01` 这个系数之所以没让模型彻底崩掉，正是因为**感知项也被未归一化 bug 削弱了**，
> 两者量级碰巧接近，看似"平衡"。这是一个**两个错误彼此掩盖**的巧合，不是设计。
>
> 而训练目标真正在学的是：**一个被归一化 bug 扭曲过的感知目标**——它既不忠实于像素，也不忠实于语义。

这解释了第 10 轮实测为什么模型 PSNR 比 bicubic 低 11 dB：
模型优化的是一个"语义上偏、像素上不管"的目标，最终画出的图自然偏离 GT。

## 三、我推翻自己在第 2 轮的一个结论（并如实记录）

第 2 轮我写过：

> 验证集用随机裁剪 → 指标不可复现，文献基线未自测。

"文献基线未自测"是对的（第 10 轮已证）。但"**随机裁剪 → 指标不可复现**"这一条，
我本轮做了定量实验，**结论的严重程度需要下调**。

用真实结构图（`sample_scene`，512×512）做 20 次随机裁剪评估：

```
20次评估: 均值=30.50  标准差=0.10  极差=0.47 dB
范围: [30.39, 30.86]
```

不同 crop 尺寸下的标准差：

| crop | 标准差 |
|------|--------|
| 64 | 0.096 dB |
| 96 | 0.104 dB |
| 128 | 0.034 dB |
| 192 | 0.035 dB |

**标准差分贝只有 0.03–0.1 dB 量级。** 也就是说：

- ✅ "随机裁剪使指标不可复现" —— **成立**（同一模型同一图，每次结果确实不同）。
- ❌ 但我此前暗示的"best epoch 判定基于噪声" —— **夸大了**。0.1 dB 的波动，不足以让"挑最佳
  epoch"变成纯粹抽签。真实图像的纹理差异会放大这个波动，但它是一个**次要问题**，
  不该和"训练目标错误"这种致命问题并列。

**本项降级为"可复现性瑕疵"，而非"指标不可信"。** 这是可复核性要求的一部分——
如果我把小问题说成大问题，懂行的人同样会不信任我。

## 四、导出链路核查：这一步是干净的

好消息要说清楚。我验证了 `train/export.py` 的 TorchScript 导出是否引入额外误差：

```
traced 两次输出差: 0.0
traced.train() 后输出差: 0.0
=> BatchNorm 统计已正确冻结（trace 的正常行为）
```

导出链路**没有引入误差**，推理端和训练端行为一致。这一环是合格的，不扣分。

**但导出链路也把"训练时的病"原样带进了服务**——包括第 10 轮发现的"假放大"语义错误，
和第 8 轮发现的低光尺寸不匹配。导出是忠实的，问题在导出之前。

另外确认了一个事实：

```
models/ 目录不存在      ← checkpoint(.pth) 未提交
train_log_*.csv 不存在  ← 训练日志未提交
```

即 **产生所有指标数字的中间产物（checkpoint、逐 epoch 日志）都不在仓库里**。
第 10 轮的"指标不可复现"，本轮从另一个方向再次印证：不是仓库忘了放，是 `.gitignore` 明确排除了它们。

## 五、还有一个未解的技术疑点：训练/推理尺寸不一致的连锁

第 8 轮发现低光训练用 `crop_size=128`、推理用整图，造成 17.6/255 的数值差。
本轮顺着超参再看一层——**这不是孤立 bug，是数据管线和模型结构耦合造成的**：

- `LowLightDataset.__getitem__`：图小于 crop 时 `resize` 到 128×128（**改变几何**）；
- `model_loader._pad_to_multiple(img, 32)`：推理时 pad 到 32 的倍数（**不改变几何，但补零**）；
- `LowLightUNet`：down 三次（每次 /2），要求输入边长是 32 的倍数。

**三处对"尺寸"的处理规则互不相同**：训练允许任意尺寸→强制 resize；推理要求整除→pad；
模型要求整除→否则解码器 concat 崩溃。这是典型的"**同一约束在三个地方被各自发明了一遍**"，
而它们之间没有单一事实来源（single source of truth）。

> 这类问题不会出现在单个文件里，只在**跨模块的契约**上暴露——也正好落在第 9 轮证明的
> "测试只测形状、不测契约"的盲区里。

## 六、本轮结论

把第 11 轮钉在几个点上：

1. **超参没病**——lr/batch/epoch 合理。问题在损失函数和归一化，不在调参。
2. **损失函数定量结果被修正**：不是"感知占 99%"，而是"像素项被×0.01、感知项因未归一化失真，
   两个错误彼此掩盖成 ~50/50"。**这是比原结论更精确、也更难被辩驳的诊断。**
3. **我推翻了自己第 2 轮把随机裁剪说成"指标不可信"的表述**——实测波动仅 0.1 dB 级，
   降级为"可复现性瑕疵"。
4. **导出链路干净**，但忠实地带走了训练阶段的所有缺陷。
5. **尺寸约束在三个模块被各自定义**，没有单一事实来源——这是"契约层"而非"代码层"的缺陷。

**统一到一句话：**

> **这个项目的问题从来不在"某个参数没调好"，而在一组"彼此掩盖、分散在多个模块、且恰好都
> 落在测试盲区里的"缺陷。** 每一个单独看都像小问题，合起来就是一个学不出东西的模型——
> 而文档只记录了"结果"，没有记录"验证"，所以这些缺陷全部存活到了发布。

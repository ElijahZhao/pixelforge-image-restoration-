
### 1.2 这意味着什么

前几轮我发现 40 项问题，**它们不是逐步积累的技术债，而是"一次性写成、从未被验证过"的结果**。

答案：因为它**是"写出来"的，不是"验证出来"的**。所有代码路径都"看起来对"，
但没有一条经过"运行 → 观察 → 对照"的检验。

> **对比**：如果项目是"渐进开发"的，通常会在某次运行中暴露问题、逐步修复。
> 但"一次性写完"的项目，bug 会**整体存活到交付**——因为它们从未与"现实"碰撞过。

## 二、H3：低光模型的新 bug——训练/推理尺寸不一致

### 2.1 问题

| 阶段 | 输入尺寸 |
|---|---|
| **训练** | `LowLightDataset` 随机 crop **128×128** |
| **推理** | `predict_lowlight` 喂**整图**（任意尺寸） |

一个在 128×128 上训练的卷积网络，被要求处理任意尺寸的整图。

### 2.2 实测

```
同一张图，分别用 512×512 和 128×128 输入：
  512 输入 → 输出亮度 137.7
  128 输入 → 输出亮度 123.5（放大后对比）
  平均差异 = 17.6 / 255
```

**输出随输入尺寸变化 17.6/255**——说明模型行为**尺寸依赖**，而非尺度不变。
这与"训练用 128、推理用整图"的分布错配直接相关。

### 2.3 与低光"过曝"的关系

第二轮发现低光输出**过曝**（亮度 137.7 vs 真值 83.4）。现在有了新解释：

- 训练时模型只在 128×128 的小 patch 上见过局部统计
- U-Net 的下采样/上采样在**不同输入尺寸下感受野/尺度不同**
- 全图推理时，模型的"全局行为"偏离了训练时的"局部行为"
- → 叠加 L1 损失对小 patch 的偏向，产生了"固定方向提亮"的退化解

> 这是**又一个"从未验证"的产物**：如果有人拿训练时相同尺寸做推理测试，会立刻发现不一致。

## 三、H4：★ 统一根因（本轮的真正价值）

### 3.1 把 40 项发现重新归类

前七轮我按"层次"（算法/前端/文档…）组织了发现。本轮我按**"为什么会产生"**重新归类，
得到一个惊人简洁的结论：

**A 类：从未"运行"验证 → bug 存活**
| 发现 | 本该如何被发现 |
|---|---|
| SR 损失权重 0.01 | 跑一次纯 L1 对照，看 PSNR 差异 |
| VGG 未归一化 | 打印 VGG 特征的非零率 |
| 低光尺寸不匹配 | 用训练同尺寸测一次推理 |
| before/after 语义（4处） | 人工看一眼对比图是否对齐 |
| DoS（225MB/39s） | 上传一张大图试试 |

**B 类：从未"对照"验证 → 假成功存活**
| 发现 | 本该如何被发现 |
|---|---|
| val 随机 crop | 固定 val，跑两次比数字 |
| 文献基准冒充自测 | 自己跑一遍基线 |
| e2e 只验长度 | 断言前先想"这能证明什么" |

**C 类：从未"同步"验证 → 文档分裂**
| 发现 | 本该如何被发现 |
|---|---|
| method page 过时 | 改 README 时检查其它引用 |
| DEPLOY.md 过时 | 换部署方式时更新所有部署文档 |
| 命名误导（srcnn/U-Net） | 导出时核对文件名与类型 |

### 3.2 收敛结论

```
A、B、C 三类，全部指向同一件事：

   ★★★ 项目缺少「验证闭环」★★★

   写代码 ──✗──> 没验证 ──> ① bug 存活（没测）
                          ──> ② 假成功存活（没对照）
                          ──> ③ 文档漂移（没同步）

   40 项发现 = 1 个根因的 40 种表现。
```

### 3.3 这个根因的性质

**关键认识：这不是"能力不足"，而是"流程缺失"。**

- 代码写得**很规整**（结构清晰、命名统一、有文档、有测试框架）
- 但**没有一条"验证"的回路**——没有"运行→观察→对照→修正"的循环

用一句话概括：

> **PixelForge 是"写出来的"项目，不是"验证出来的"项目。**
> 它的作者会写代码，但还没有养成"让代码与现实碰撞"的习惯。

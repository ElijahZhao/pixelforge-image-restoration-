# PixelForge 诊断报告 · 第 9 轮

**主题：测试套件是"形式验证"还是"实质验证"——一次变异测试实验**

> 本轮不新增功能、不改任何代码，只做一件事：**验证"验证本身"是否有效**。
> 前 8 轮找到了约 44 个真实缺陷。第 9 轮问一个更根本的问题：
> **"这个项目有测试，为什么这些 bug 能全部活下来？"**

## 二、实验设计：变异测试（Mutation Testing）

**方法**：故意向代码里注入"已知的致命错误"（变异体），然后运行现有测试套件。
- 若测试**失败** → 说明测试能拦截这类错误 → 记为 `拦截 ✅`
- 若测试**仍然全绿** → 说明这类错误会从测试眼皮底下溜走 → 记为 `漏掉 ❌`

这是软件工程里判定"测试到底是真验证还是走过场"的黄金标准。**只读**：所有变异都在 `/tmp/mut/` 的副本上进行，原仓库未被改动。

## 三、实验第一组：模型结构 / 指标公式类变异

| 编号 | 注入的错误 | 错误性质 | 测试反应 |
|------|-----------|---------|---------|
| M1 | `SRGenerator` 残差块 `8 → 1`（容量砍掉 87%） | 模型严重退化 | ❌ **漏掉** |
| M2 | SR 上采样 `PixelShuffle(scale) → PixelShuffle(1)` | 输出尺寸错 | ✅ 拦截 |
| M3 | U-Net 去掉残差学习 `x + out → out` | 语义巨变，形状不变 | ❌ **漏掉** |
| M4 | PSNR 系数 `10·log10 → 20·log10` | 经典公式错误 | ❌ **漏掉** |
| M5 | PSNR 漏掉平方 `max_val² / mse → max_val / mse` | 公式错误 | ❌ **漏掉** |
| M6 | SSIM `ssim_map.mean() → .sum()` | 数值比例错 | ✅ 拦截 |

**拦截率：2/6**

## 五、两个实验合起来说明什么

**总拦截率：4 / 10。**

而这 4 次"成功拦截"，有一个共同规律——**它们全部是"改变输出形状或导致维度崩溃"的错误**：
- M2 `PixelShuffle(1)` → 形状从 128×128 变成 32×32 → 形状断言炸了
- M6 `.sum()` → SSIM 值超出被断言的区间 → 范围断言炸了
- D1 去掉上采样 → 形状错
- E1 通道 3→6 → 形状错

而**所有 6 次"漏掉"的错误，有一个共同规律——它们不改变形状，只改变"内容/语义/数值"**：
- M1 容量退化：形状 128×128 不变，只是变成一个更笨的模型
- M3 去掉残差：形状不变，但学的东西完全变了
- M4/M5 指标公式错：返回的还是 float，只是数值错了
- A1 损失权重：训练照跑不误，只是训练目标错了

**结论（本轮最硬的发现）：**

> **这个测试套件本质上是一套"形状测试"（shape test），不是"正确性测试"（correctness test）。**
> 它唯一能保证的是"代码不会因为维度错误而崩溃"，
> 它**无法保证模型学到了正确的东西、指标算得对、训练目标没写错**。

这正好解释了为什么第 1~8 轮找到的**全部 44 个缺陷中，涉及"数值/语义/训练目标"的那一大类，全都能通过测试**——因为测试压根不看这些。

回看 `test_models.py` 的断言：

```python
def _assert_shape(model, x, expected, label):
    y = model(x)
    assert list(y.shape) == expected       # 只检查形状

def _assert_range(y, label):
    assert y.min() >= -1e-5 and y.max() <= 1.0 + 1e-5   # 只检查范围
```

7 个模型测试里，**没有一条断言涉及"模型输出是否正确"**。它们检查的是：
形状对不对、值在不在 [0,1]、是不是正确的类、batch 内是否一致。
——全部是"结构属性"，没有一条是"功能属性"。

## 六、对第 8 轮根因的修正

| | 第 8 轮（旧） | 第 9 轮（修正后） |
|---|---|---|
| 表述 | 项目缺失验证闭环 | 项目**有**验证，但验证的是**形式**不是**实质** |
| 证据 | 未做实验 | 变异测试：10 个致命注入只拦截 4 个，且全是形状类 |
| 含义 | "没检查" | "检查了，但检查的是不会出错的地方" |

**修正后的统一根因：**

> **验证存在于形式，缺失于实质（verification exists in form, not in substance）。**
> 项目的每一个环节——单元测试、e2e 测试、demo 脚本——都在"运行"，
> 并且都会"通过"。但它们通过的原因，恰恰是因为它们只检查了最不可能出错的维度（形状/范围/能否跑通）。
> 真正的错误（训练目标、归一化、尺寸语义、前后端语义、资源边界）全部落在这层验证的**盲区**里。

这比"没有验证"更值得警惕，也更接近一个**懂行的人会一眼看穿的东西**：
> 一个项目"测试全绿"却学不出正确的模型——通常不是巧合，而是测试在自欺。

## 七、这条发现的"含金量"在哪

本轮的价值是：

1. **它把散落的 44 个 bug 收束到一个可以一句话讲清、且可复现证明的机制**——不是"这里写错了那里写错了"，而是"验证系统性地避开了所有会出错的地方"。
2. **它是可证伪的**：任何人都可以用同样方法（注入变异、跑测试）验证这个结论，不需要相信我。
3. **它指向的修复方向完全不同**：不是"再补几个 bug fix"，而是"先让验证真的能失败"——即先建立**会红的测试**（golden test / 已知答案测试 / 回归测试），否则任何修复都无法被证明有效。

# PixelForge 诊断报告 · 第 10 轮

**主题：数据与指标的真实性核查——"真实评测值"到底真在哪**

> 前 9 轮查了代码、测试、部署链路，都绕开了最根本的东西：**数据和数字**。
> 一个模型项目能不能"经得起懂行的人盯着看"，最终要落在一句话上：
> **"你说的这些 PSNR 数字，是不是真的？模型真的有那个能力吗？"**
> 本轮不依赖任何文档自述，直接解包权重、跑评测、复现数字。

---

## 一、先看事实：仓库里根本没有训练数据

```
$ find data -type f
data/README.md          ← 只有这一个文件

$ find results -type f
results/README.md       ← 只有这一个文件
```

`data/` 和 `results/` 里**各只有一个 README**，没有任何真实图片、没有任何训练日志 CSV。

这不一定是问题（大数据集本就不该提交进 git，`.gitignore` 也写了 `data/div2k/`、`data/lol/`、`results/*.csv`）。但它带来一个后果：

> **项目的所有指标数字，都无法在这个仓库里被复现。**
> 因为产生这些数字的输入（DIV2K / LOL 数据集）和过程（训练日志）都不在。

于是"17.20 dB / 19.26 dB"这几个数，**在仓库内部是不可证伪的**——你说它是真的，我无法用仓库里的东西验证；你说它是假的，也无法证伪。这本身就是"懂行的人会立刻注意到"的第一个点。

---

## 二、但是——权重是真的训练过的

我不靠文档，直接解包 `serve/models/*.pt` 的内部结构：

```
sr_generator_scale4.pt   5,031,991 bytes   264 inner entries
lowlight.pt              2,308,978 bytes    93 inner entries
```

内部张量名包含：

```
res_blocks.body.running_mean / running_var / num_batches_tracked   ← BatchNorm 统计量
```

**关键推论**：`running_mean`/`running_var`/`num_batches_tracked` 是 BatchNorm 在训练中被更新的统计量。
- 如果权重是随机初始化，`num_batches_tracked` 会是 0，`running_mean` 会是 0、`running_var` 会是 1。
- 这些量被真实更新过，说明**模型确实在真实数据上跑过训练循环**。

所以结论是：**模型不是假的、不是随机权重**。这一点必须承认，不能为了"找问题"而抹黑。（第 7 轮的权重统计也支持这一点。）

---

## 三、可是——模型的能力是真的不行（可复现实验）

既然权重是真的，那就直接测它能干多少活。**用仓库自带的图，走标准 SR 评测流程**：

```python
# 取 sample_scene 中心 256×256 作为 GT
# LR = bicubic 下采样 4 倍 -> 64×64
# 分别用 纯bicubic 和 模型 放大回 256×256，与 GT 比 PSNR/SSIM
```

**SR ×4 实测结果：**

| 方法 | PSNR | SSIM |
|------|------|------|
| Bicubic 放大（什么都不做） | **33.25 dB** | **0.8155** |
| PixelForge SRResNet ×4（自训） | **22.06 dB** | **0.3168** |

> **模型比"什么都不做"还差 11.2 dB，SSIM 只有 bicubic 的 39%。**
> 而且这还是在内容极简单的合成图（见第六节）上——真实照片上差距只会更大。

这说明第 8 轮的"训练目标错了"不是学术讨论，是**肉眼可见的后果**：模型输出的 PSNR 远低于最简单的基线。

**低光增强实测（同一张图，GT=原场景，dark=input×0.16）：**

| 方法 | PSNR | SSIM | 输出亮度 |
|------|------|------|---------|
| 自适应伽马（经典基线） | **19.62 dB** | **0.8712** | 98.6 |
| PixelForge U-Net（自训） | **12.68 dB** | **0.7124** | **137.7** |
| GT 参考 | — | — | 83.4 |

> 模型输出亮度 137.7，**比 GT 亮 65%，严重过曝**；PSNR 12.68 **输给经典 gamma 基线 6.9 dB**。

**这两组数字，直接反驳了文档的核心卖点。**

## 四、文档与现实的对账（逐条）

| 文档声明 | 出处 | 实测结论 |
|---------|------|---------|
| "All (ours) rows are **REAL measured values**" | `results/README.md` | 权重真、训练真，但**数值无法在仓库复现**（无数据/无日志） |
| SRResNet ×4 = **17.20 dB**（"刻意牺牲像素换观感"） | `README.md` / `results/README.md` | 独立复现：**22.06 dB**，且**输给 bicubic 33.25 dB**；"刻意牺牲"解释不成立 |
| U-Net = **19.26 dB**，"明显胜 gamma 基线" | `README.md` / `PROGRESS.md` | 独立复现：**12.68 dB**，**输给 gamma 基线 19.62 dB**；"胜出"结论反向 |
| "低光 U-Net 已验证胜出" | `README.md` 第 140 行 | 实为**模型输给基线** |
| Bicubic 2× = 33.66（标 `*` 文献值） | 指标表 | 该值来自 Dong et al. 在 **Set5** 上，与本项目无关（第 8 轮已指出）；且**未自测** |
| 低光基线 "≈15–17 dB"（标 `†`） | 指标表 | 文档自己承认"**未在本项目测试划分上自测**"——即这是个凭印象写的区间 |
| "SRCNN 2× = TBD" | 指标表 | 文档自承"未训练"——即 SR 的经典基线条目其实空缺 |

**最要命的一条**：`README.md` 第 122 行辩解 SR 的低 PSNR 是"VGG 感知损失刻意牺牲像素精度换观感，**非 bug**"。
但第 1、3 轮已经证明：感知损失权重代码是 `loss = 0.01 * loss + percep(out, hr)`，**感知项占 99%**，且 **VGG 输入未归一化**（91.6% 特征为零）。
所以这不是"刻意的配置选择"，而是**一个被掩盖的 bug 被包装成了设计**。文档把一个缺陷说成了'取舍'。

## 五、还有一个更隐蔽的"假放大"（第 5 个语义错误实例）

前 4 轮在 `make_demo.py`、`serve/app.py`、前端、Gradio 里发现过 SR 语义错位。本轮在**推理库内部**又找到一个，而且最隐蔽：

`serve/model_loader.py::predict_sr` 的真实逻辑（逐步实测）：

```
1. 输入 512×512 图
2. 内部先 bicubic 下采样到 128×128   (img.width // scale)
3. 模型(128×128) -> 真实输出 512×512  (只放大 4 倍，这是模型的真实能力)
4. 最后 PIL 再 .resize 到 512*4 = 2048×2048  ← 这一步是纯插值
```

```python
out = out.resize((img.width * scale, img.height * scale), Image.BICUBIC)
#                 ^^^^^^^^^^^^^^^^^^^^ 512*4 = 2048
```

**实测确认：**

```
1. 内部 LR:            (128, 128)
2. 模型真实输出:        (1, 3, 512, 512)
3. clamp 后 PIL:       (512, 512)
4. 最终返回:           (2048, 2048)   ← 512×4
```

> **对外返回 2048×2048，但模型真正只产出了 512×512。**
> 中间 512→2048 那 4 倍，是 PIL 的 BICUBIC 插值，**不是模型能力**。
> 用户以为"得到了模型 ×4 的 2048 高清图"，实际上模型只做到 512，剩下的是普通放大。

这是一个**会把"模型效果"虚报 4 倍的语义错误**，且藏得极深——它不在 demo 脚本里，而在被所有调用方共用的推理函数内部。

## 六、连"真实 demo 图"本身也是代码画的

文档反复强调 demo 图是"**CPU 上用本仓库真实权重跑出的输出**"（这句话是准确的——确实是权重跑出来的）。
但"输入图"本身呢？看 `scripts/make_demo.py::make_scene`：

```python
def make_scene(size=512):
    """A simple, photo-like synthetic scene: sky gradient, sun, mountains."""
    ...浅色渐变天空 + 一个圆当太阳 + 两个多边形当山 + 高斯噪声
```

**它不是任何真实照片，是用 numpy 画出来的合成图。** 实测它的复杂度：

```
独特颜色数: 59,898 / 262,144 像素 (22.8%)
平均水平梯度: 2.638   垂直梯度: 2.685
图像均值: 83.4/255   标准差: 36.8
```

**含义**：这是一张渐变+两块纯色多边形+噪声的图，细节极少。
- 在这种"几乎无高频细节"的图上，SR 本来就没有多少东西可还原——**恰好掩盖了模型的弱点**。
- 而这已经是项目能拿出的"最好看"的展示了。

> 换句话说：项目用一个**人造的、过分简单的合成图**作为唯一视觉证据，
> 在这张图上模型**仍然输给 bicubic 11 dB**。
> 这已经不是"效果不够惊艳"，而是"效果为负"。

## 七、本轮结论

把第 10 轮和前面 9 轮拼起来，一个完整的图景浮现：

1. **工程外壳是真的**：权重真实训练过（BN 统计量为证）、代码能跑、测试能过、部署能上线。
2. **指标数字是"真但不可复现"的**：训练确实发生过，但产生数字的数据与日志都不在仓库里，无法验证。
3. **模型的真实能力是负的**：在可比条件下，SR 输 baseline 11 dB，低光输 baseline 7 dB。
4. **文档用"取舍/设计选择"的语言，掩盖了真实的缺陷**（感知损失 bug 被说成"刻意换观感"）。
5. **最隐蔽的语义错误在推理库内部**，把模型能力虚报 4 倍。

**统一到一句话**（这是第 10 轮的收束）：

> **这个项目最真实的处境是："它证明了自己能跑通一条 MLOps 流水线，但没有证明这条流水线产出的模型是有效的。"**
> 而更关键的是——**项目用文档的措辞，把'没验证有效'叙述成了'已验证有取舍'。**

对"经得起懂行的人盯着看"这个目标，最后这一点才是真正的软肋：
懂行的人不会因为你 PSNR 低就否定你，但会因为你**把 22 dB 说成 17 dB 的"刻意取舍"、把 12.68 dB 说成"胜出"**而失去信任。
**技术可以弱，叙述不能虚。**

# DIAGNOSIS ROUND 20 — 低光增强「越增强越暗」

## 现象

用户上传一张游戏截图（水母场景），选择 **Low-Light Enhancement**，结果 **After 比 Before 更暗**：
背景蓝色变深、暗部细节丢失、噪点/压缩伪影被放大。而另一张明亮插画则「看起来没问题」。

## 复现与量化

用用户截图中的水母原图（777×569）在本地跑模型，并与经典基线对比（真实像素统计）：

| | 输入 | 经典自适应伽马 | **自训 U-Net** |
|---|---|---|---|
| 平均亮度 | 0.412 | 0.451 ↑ | **0.337 ↓** |
| 中位数 p50 | 0.260 | 0.316 ↑ | **0.059 ↓↓** |
| p90 | 0.968 | 1.000 | 1.000 |

**模型把亮度中位数从 0.26 压到 0.06**，同时把高光顶到 1.0 —— 即压死暗部、增大对比度、
放大伪影。经典基线方向正确（正常提亮）。

早期用纯色块测试时模型总是「变亮」，因此该问题**只在真实内容上出现**，纯色合成图无法复现
——这也是最初漏判的原因。

## 根因：训练域与实测域不匹配

低光 U-Net 训练于 **LOL-v1**（真实夜间**照片**）："低光" = 传感器缺光、带特定噪声与伽马特征。
模型学到的是 `欠曝真实照片 → 正常曝光真实照片`。

用户输入是**游戏截图**：合成平面色块、故意的深蓝背景、本身不存在"欠曝"。
模型把大块深蓝当作"欠曝夜景"，套用其学到的照度校正；由于输入没有真实噪声可恢复，
它只能**拉伸对比度、压死暗部**，于是画面变暗。

> 这是与 SR「双次降采样」同一类问题：**模型在认真执行它被训练的任务，只是不该用这类输入触发它。**

## 附带发现（已修复）：非 32 倍数尺寸的黑边光晕

U-Net 多次下采样，输入边长必须被 32 整除。900×600 直接抛：

```
RuntimeError: Sizes of tensors must match except in dimension 1.
Expected size 226 but got size 225 for tensor number 1 in the list.
```

原有 `_pad_to_multiple(img, 32)` 用 **0（黑）填充** 避免崩溃，但黑边是模型在 LOL
训练数据里**从未见过的假边缘**，它会去"修正"这条边，从而在被填充的一侧留下可见接缝。

实测（400×300 夜景照片，pad 16×20）：

| 填充方式 | 边缘 vs 内部亮度差 | 蓝色偏置 |
|---|---|---|
| **0（黑，原实现）** | **0.094** | **+0.106** |
| 反射（现实现） | **0.010** | +0.023 |

改用 **`np.pad(..., mode="reflect")` 边缘反射** 填充后，接缝下降 **89%**、蓝色偏置下降 **78%**。

> 注意：`ImageOps.expand(fill=None)` 仍是黑色，无法做边缘复制 —— 真正的反射必须走 numpy。

## 修复（方案 A + B）

**A. 曝光门控（自动回退）**

新增 `looks_underexposed(img)`：**同时**要求

- 第 10 百分位 `p10 ≤ 0.22`，且
- 平均亮度 `mean ≤ 0.36`

只有两者都满足才判定为"真实欠曝"，才调用自训模型；否则回退经典自适应伽马基线，
并在 UI 明确说明原因。

**为什么必须同时看 p10 和 mean**：水母截图的 `p10 = 0.058`（与真实夜景相当，因为有大片深色背景），
但其 `mean = 0.412`（明亮）。只看 p10 会把它误判为欠曝。

阈值验证：

| 输入 | mean | p10 | 判定 |
|---|---|---|---|
| 合成夜景照片 | 0.105 | 0.074 | ✅ 欠曝（启用模型） |
| 水母游戏截图 | 0.412 | 0.058 | ✅ 非欠曝（回退基线） |
| 近白图 | 0.980 | 0.980 | ✅ 非欠曝 |
| 明亮暖色 | 0.802 | 0.802 | ✅ 非欠曝 |

**B. 低光三图对比**

当模型实际运行时，展示 ① 输入 / ② classical 自适应伽马基线 / ③ 自训 U-Net，
并附说明：若 ③ 比 ① 更暗，说明该图不在模型训练域内，② 是更稳妥的选择。

# DIAGNOSIS ROUND 21 — 输入门控不够，补输出守卫

## 现象

Round 20 的输入门控上线后，用户又用**同一张水母游戏截图**测试，模型**仍然被启用并把画面变暗**。

## 为什么输入门控失效

实测该输入：`p10 = 0.055`、`mean = 0.227` —— **两个条件都满足**，因此门控放行。

根本原因：**这张图确实很暗**。输入侧的曝光检查无法区分

- 「该被提亮的暗照片」
- 「该保持原样的暗色美术图」

而且它也不该试图区分 —— 曝光值本身不携带"是不是照片"的信息。

## 更好的信号：比较模型输出与输入

任务叫「低光**增强**」。若模型输出比输入**更暗**，该结果本身就自相矛盾，
无论输入是什么。实测该信号的区分度极大：

| 输入 | 平均亮度变化 Δ | 判定 |
|---|---|---|
| 真实夜景照片 | **+0.468** | ✅ 模型确实在增强 |
| 水母游戏截图 | **−0.021** | ❌ 变暗 |
| 明亮截图 | **−0.076** | ❌ 变暗 |
| 桌面截图 | +0.096 | ~轻微 |
| 星空卡片 | +0.033 | ~轻微 |

真实夜景提亮 **+0.47**，而所有失败案例都是负值 —— 界限非常清晰。

## 修复：两层守卫

1. **输入门控**（保留）：只对"有可能欠曝"的图才跑模型 —— 省算力，但**不充分**。
2. **输出守卫**（新增，关键）：跑完后比较 `mean_luminance(model_out)` 与
   `mean_luminance(input)`，若增益 `< 0.005`（即基本没变亮甚至变暗），
   **丢弃模型输出**、改用经典基线，并给出专门说明。

输出守卫**自验证**，不依赖任何输入分类，因此不会被"暗色美术图"绕过。

## 阈值

```python
LOWLIGHT_DARK_P10 = 0.22
LOWLIGHT_DARK_MEAN = 0.36
LOWLIGHT_MIN_GAIN = 0.005   # 模型输出相对输入的最小亮度增益
```

- `serve/model_loader.py` — `mean_luminance()` / `LOWLIGHT_MIN_GAIN`
- `serve/app.py` — 低光分支接入输出守卫，`guard_rejected` 走专门 note
- `deploy/hf_space/app.py` — 同上门控 + 输出守卫

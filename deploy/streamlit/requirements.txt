# ---------------------------------------------------------------------------
# WHY THIS FILE EXISTS SEPARATELY FROM THE ROOT requirements.txt / requirements.lock.txt
# ---------------------------------------------------------------------------
# This is the dependency set for the Streamlit Community Cloud demo only. It is
# intentionally NOT derived from the root lock because the two runtimes differ:
#   * The root lock serves the FastAPI inference service + training scripts and
#     pulls the CUDA-capable torch that training/serve expect.
#   * This app runs CPU-only on Community Cloud (~2.7 GB RAM, no GPU), so it pins
#     a CPU-only torch (see below) and carries nothing training-related.
# Keeping the two independent avoids dragging CUDA/nvidia packages (19 of them)
# into the free tier, where they are dead weight that can OOM the pod. If you
# change torch here, re-pin both lines together; do not "reuse" the root lock.
# ---------------------------------------------------------------------------
# st.image(..., width="stretch") — used throughout the result panels — needs the
# modern width API, which landed in 1.49.0 (it is `width: Width = "content"`).
# In 1.40–1.48 `width` is `int | None` and only `use_container_width` existed, so
# the string "stretch" is rejected and the whole result area raises. Do NOT lower
# this floor back to 1.30/1.40.
streamlit>=1.49

# ---- torch: CPU-only, pinned ----
#
# Streamlit Community Cloud gives this app ~2.7 GB RAM and NO GPU, so
# `torch.cuda.is_available()` is always False and the CUDA runtime is dead weight.
# A plain `pip install torch` pulls the CUDA build, which drags in 19 nvidia/cuda
# packages (nvidia-cublas, nvidia-cudnn-cu13, cuda-toolkit, triton, ...) that are
# never executed here but still occupy memory on a tier that cannot spare it.
# The deploy logs list all 19 (the diagnostic write-up is kept in the private archive).
#
# `--extra-index-url` makes pip prefer the CPU wheels from PyTorch's own index.
# The upper bounds pin the version: without them a redeploy silently picks up
# whatever is newest (the live app had drifted to torch 2.14.1, whose
# `torch.jit.load` is already deprecated). The weights are TorchScript and
# hardware-independent, so the CPU build produces bit-identical output.
--extra-index-url https://download.pytorch.org/whl/cpu
torch>=2.0,<2.5
torchvision>=0.15,<0.20

numpy>=1.23
Pillow>=9.0
